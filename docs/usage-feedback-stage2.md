# 第 2 阶段：使用会话与反馈

沿用现有 Flutter/Provider、SQLite 和 BLE 字符串协议。新增 `UsageSessionService` 管理真实控制流程，原 `UsageRecordService` 保留查询和模拟测试兼容入口。AI 尚未接入此服务。

## 用户流程

1. 首页首次开启风扇时，可填写使用前舒适程度和场景，确认后发送指令；留空不会记成零分。
2. 一次连续使用共享一个会话。各风扇分别保存开始、结束和气味快照；中途添加、关闭及重新开启都会保留区间。
3. 最后一路关闭、全部关闭或紧急停止成功后结束会话，进入反馈页面。
4. 反馈包含使用前/后舒适程度、喜欢程度、再次使用意愿和一句话感受。使用前漏填时可回忆补填，标记为 `recalled`；开始时已填的值不能事后改写。
5. 用户可暂不反馈，通过首页“使用反馈”补填或编辑；保存反馈无需收藏，也可另存为气味瞬间。

反馈按会话唯一存储、按用户归属查询。保存/修改时增加 `preference_profiles.input_version` 并置为 `pending`，为下一阶段的重新评分和 AI 更新提供失效标记；本阶段不会调用 AI。

## 指令与数据一致性

- 使用开始前先写 `pending` 记录；取消旧定时及开启指令成功后更新为 `active_unverified`。失败保留尝试记录但不计成功时长。
- 同一服务串行处理控制与定时，快速重复开启不会产生重复使用记录。
- 全部关闭和紧急停止都经过服务并统一结束各路记录。
- 单路/全部关闭发送失败时不宣称已结束。若重试成功，之前的不确定区间不生成可信时长。
- 重启时将遗留的活动会话标为 `interrupted`，不补算 APP 退出期间的时长，不自动操作硬件。
- 断连时记录中断，取消本地定时；重新连接后用户可通过“全部关闭”恢复设备状态。
- 活动会话期间禁止修改气味配置，历史快照不随当前配置变化。

## 定时

数据库增量升级至 v11，给 `usage_records` 增加 `timer_end_time`。新建、v9 升级、v10 升级均沿用同一入口。

沿用 `fanN_off_毫秒` 和 `fanN_cancel`。每次重新开启前发送取消旧定时，避免旧硬件定时影响新使用。本地取消/替换定时会使旧回调失效。

到期时尝试补发关闭指令并结束对应记录；由于没有硬件状态回执，定时区间标为 `timer_elapsed_unverified`，会话标为 `completed_estimated`，时长保留未知。到期无法发送时转为中断，并提示重新连接后关闭。

## 可信度与限制

当前协议只能确认 BLE 写入，不能确认风扇物理运行。`completed_unverified` 表示正常完成 APP 指令流程，不代表硬件已验证。所有不确定数据保留来源/状态，后续推荐引擎必须按状态筛选。

多路重叠时会话时长不相加。快照保存完整各路区间；多段组合的会话不赋予单一 `combination_key`，后续评分不能把整次好评复制给每个子组合。

APP 被系统暂停时本地回调可能延迟，重启后不会恢复旧的本地倒计时；设备侧定时协议是否按预期执行仍需 ESP32 真机验证。

## 验证

`flutter test --no-pub`：数据库迁移、失败开始/关闭、串行控制、多路会话、取消/替换/到期定时、断连/重启、用户隔离、反馈编辑失效及表单交互。使用临时 SQLite 数据库及模拟指令发送器，不连接真实硬件。

Windows 沿用项目的 SQLite system 配置，测试进程需能找到 `sqlite3.dll`。本机运行测试临时将 `C:\Python314\DLLs` 加入进程 PATH，没有修改系统 PATH。
